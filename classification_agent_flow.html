Outlook Support Classification Agent — Foundry v2

A Microsoft Foundry agent that classifies a user's Outlook issue to a knowledge-base article. On each search the function hands the agent the whole local KB — shaped exactly like the ServiceNow KB search API — and the agent itself picks the match. No LLM re-ranker.

Endpoint  POST /api/outlook-classification-v2 Input  { conv_id?, message } Output  { conv_id, status, agent_message, kb_id, summary, chat_close } KB  ServiceNow-shaped kb_index.json Agent  clasification-agent-v2 Auth  Managed Identity — no keys

1 The idea in one line

A user describes an Outlook problem in plain English. The agent clarifies if needed, then reads the knowledge base and returns exactly one outcome: a matched KB article (routed by its number), a clarifying question, or a polite human hand-off — every match traceable to a real article, and the user only ever sees a friendly message (never article internals).

v2: the agent is the selector (no re-ranker)

On search, the function returns the entire local KB to the agent and the agent chooses by reading the article content. There is no Azure OpenAI ranker and no relevance score — one fewer model call, no scoring heuristics.

POC ⇆ production seam

The local kb_index.json mirrors the ServiceNow search-result shape (number + full "Article Content"). In production the search step becomes a real ServiceNow API call returning the same shape — only the KB source swaps; agent, prompt, grounding and response stay identical.

The per-turn reply is a strict JSON object. One status (search) is a private instruction to the function; the other three are shown to the user.

Names the user's task, logs a summary of their issue; a person follows up. Chat closes.

4 The in-process loop & safety rails

turn_orchestrator._run_turn_loop — bounded (never infinite) and guarded (never returns a made-up article).

A

Ask the agent

Send the user message (or fed-back KB / a nudge) into the conversation; parse the strict-JSON reply.

▼
B

status = search → return the WHOLE KB (no ranker)

get_all_candidates() returns all records; the agent reads their "Article Content" and decides. Because every search returns the full set, the agent effectively classifies after one search; the max_search_rounds budget still guards the loop.

▼
C

status = resolved → grounding guard

Accept the kb_id only if it's a real number in the index (is_known_kb_id). If fabricated: nudge the agent back to real numbers (budget left) or return a safe no_match.

▼
D

Terminal reply → response

follow_up / resolved / no_match map to the HTTP response; a hard backstop closes with no_match if the loop is ever exhausted.

5 Request / response contract

New issue → no conv_id; continue by echoing the same conv_id until chat_close: true. Off-topic / misuse: steer back each turn, then a polite no_match wind-down after ~8–10 unproductive turns.

6 Ingestion — building the ServiceNow-shaped KB

A one-time, local, no-LLM step turns your KB documents into the exact structure the agent expects.

kb_source/
one KB####.docx per article (e.g. KB0024755.docx) — the KB number is the filename
ingest
python ingest_kb_articles.py — reads each doc's full text verbatim (python-docx)
kb_index.json
ServiceNow shape: { "searchResults": [ { "columns": [ …, {"fieldName":"number","value":"KB0024755"}, {"fieldName":"text","label":"Article Content","value":"<full text>"} … ] } ] }
runtime
servicenow_kb_source loads it and returns all records on search; number + "Article Content" are the load-bearing fields (sys_id / dates / category are placeholders)
